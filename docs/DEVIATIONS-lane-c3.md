# DEVIATIONS — lane C3 (battle scene as event-log renderer)

Departures from `docs/build-doc.md` / `docs/content-bible.md` made inside lane C3's file scope, plus
the core gaps C3 could not close and reported instead. Indexed from `docs/DEVIATIONS.md`.

Lane C3's files: `game/battle-view.ts`, `game/battle-input.ts`, `game/scenes/BattleScene.ts`,
`game/ui/{BattleHud,BattleFx,BattleLayout,BattleMenuPanel,BattleMessageBox,Palette}.ts`,
`tests/unit/battle-view.test.ts`.

Per build-doc §16 G12, nothing here is stated in human engineering-hours.

## Deviations

| # | Spec ref | Deviation | Rationale |
|---|---|---|---|
| C3-D1 | build-doc §16 G11 | **`VIEW_TIMING` (game/battle-view.ts) and the HP-band thresholds `HP_BAND_WARN` 0.5 / `HP_BAND_CRITICAL` 0.2 (game/ui/BattleHud.ts) are NOT in `data/balance.json`.** Nor is `MONO_ADVANCE_RATIO`, nor any pixel offset in `game/ui/BattleLayout.ts`. | G11 governs constants the **sim** reads — anything a retune of balance is supposed to move. An animation duration in milliseconds, a colour-band threshold and a pixel offset are presentation: a balance retune must not be able to change how fast the bar drains, and re-pacing the battle must not be able to move a damage number. Nothing in `core/` reads any of them, and `no_magic_numbers` (tests/gates/guardrails.test.ts) is scoped to `core/`, so this is an explicit narrowing of G11's letter rather than an unnoticed hole. Each is declared in one table with the reason written beside it. |
| C3-D2 | build-doc §9.7 / lane B | **The battle-sprite asset key is assumed to be `battle/<lineId>/<ageClass>/<front\|back>`** (`battleSpriteKey`, game/ui/BattleHud.ts). | build-doc §9.7 (corrected by D2 to 150 sprites) counts 75 forms × front/back, where a form is a (line, age-class) pair — so the key is exactly that tuple. It is built from data at runtime, so no species name is written in `game/` (§8.3 / G2), and until lane B ships, every one resolves to the shared labelled placeholder naming that exact manifest row. If lane B chooses a different key, this one function changes. |
| C3-D3 | core/types.ts `actionRejected.reason` | **`illegalActionReason`'s strings are never drawn.** The scene records the last one (`BattleScene.lastRefusal()`) and paints the row grey; it prints nothing. | core/types.ts says of that field: "it is a diagnostic, not player-facing copy (G7)". The first cut pushed it into the narration line, so the player read `the active battler has fainted — only a switch is accepted` and `"salve" is not a battle medicine (balance.medicine)` as the story of the fight, and — with no `else` branch — the line then persisted while the cursor sat on legal rows. The greyed row is the player-facing answer. **A player-facing refusal string would be content, and neither document provides one** — see the gap G4 below. |
| C3-D4 | bible §11 items | **Bag / snare / bait rows are labelled by typesetting the id** (`itemLabel`, game/battle-view.ts): hyphens and underscores become spaces, each word is capitalised. | `data/` carries no item-name table — `balance.medicine` carries ids (`salve`, `tonic`), snare tiers come from `SNARE_TIERS`, and bait ids are whatever is in the bag. The first cut printed the raw ids as labels. Typesetting an id coins no noun and adds no word, so G2 is untouched; `BattleMenuLabels.item` / `BattleViewNames.item` override it the day a name table exists. |
| C3-D5 | build-doc §7.4 renderer contract | **Every `ViewStep` carries `playerAt` / `enemyAt`** — the display state of the fielded pair at that point in the log — and the scene paints from those, never from `BattleView.snapshot`. | `push(events, stateAfter)` advances the snapshot to the end of the whole reducer step before a single step is drawn, so any mid-playback read of it is a read of the future. Reproduced in the running game: a self-buff step painted the player at 0 HP two steps before the blow that emptied them was drawn. The steps already carried the fielded *uids* for the same reason; carrying the state is the same fix, finished. |
| C3-D6 | build-doc §7.4 / §10 | **The named test file now executes `game/scenes/BattleScene.ts`** against a stub Phaser (`vi.mock("phaser")`), replaying a whole recorded fixture through the real scene. | The first cut asserted the scene by reading its own source with regexes, on the stated grounds that it value-imports Phaser. Every one of the five MAJOR defects a later audit reproduced lived in that file and in `CombatantPanel`'s Phaser half — code no test executed. A source scan cannot see a bar tweening from the wrong start value, a sprite destroyed without its panel, or a 9px z-order collision. The source scans are kept; they are no longer the only witness. |

## Gaps in `core/` that C3 could not close (reported, not worked around)

| # | Where | What is missing | Consequence today |
|---|---|---|---|
| C3-G1 | `BattleEvent.levelUp` (core/types.ts:404) | The new **`maxHp` / `curHp`**. `core/battle.ts:944-945` raises both from `effectiveStats` — a rules function the view may not call. | The view re-reads `maxHp` off the `BattleState` the reducer returned (`BattleViewAbsolutes`), which is correct because nothing else changes `maxHp` inside one reducer step. **`curHp`'s matching rise is still not knowable at the moment of the level-up**: the card shows the pre-level `curHp` against the post-level `maxHp` for that one step and is corrected at the end-of-step resync. Closing it properly is one field on the event. |
| C3-G2 | `BattleEvent.moveUsed` (core/types.ts:388) | The move's **target**. | `ViewStep.attack` has no `targetUid` at all. The first cut inferred "the other active battler", which is wrong for the five shipped self-targeting moves (harden / quicken / focus are `target:"self"`, regrow is a self-heal, burrow-roost a self-evade). A projectile or beam animation is not implementable until core logs the target. |
| C3-G3 | `BattleInput` (core/types.ts:319-328) and `BattleEvent.battleStart` (:386) | Any **trainer / gym-leader identity**. | A gym battle cannot be announced by the leader's name. It used to open "Gym battle: Nibbin" — the leader's first creature. It now opens "Gym battle" and stops, and `BattleViewNames.opponent` lets the caller supply the name. This lands on the never-cut gym demo beat, so it is the most visible of the three. |
| C3-G4 | build-doc / bible | Any **player-facing refusal copy**. | Per C3-D3 the diagnostic strings are not drawn, so a greyed row explains itself only by being grey. Writing a player-facing line here would be inventing content. |
| C3-G5 | `game/main.ts` (not lane C3's file) | `BattleScene` is **not registered** in `SCENES`. | The battle screen is unreachable from the shipped app, which is why the defects above were not seen until an auditor registered it in a throwaway entry point. Registering it is C1's one-import-one-entry change, as `game/main.ts`'s own comment describes. |
| C3-G6 | shipped fixtures | Ten of the twenty-two `BattleEvent` kinds — `heal`, `statusApplied`, `statusTick`, `statusSkip`, `statusCleared`, `statChanged`, `itemUsed`, `levelUp`, `evaded`, `actionRejected` — are produced by **no** recorded fixture. | Those paths are covered by hand-built logs and by a synthetic one-of-each replay through the real scene, which is weaker than a recorded fight. A fixture that heals, statuses, buffs and levels up would make the whole compiler fixture-covered. |
