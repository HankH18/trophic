# DEVIATIONS — lane C3 (battle scene as event-log renderer)

Departures from `docs/build-doc.md` / `docs/content-bible.md` made inside lane C3's file scope, plus
the core gaps C3 could not close and reported instead. Indexed from `docs/DEVIATIONS.md`.

Lane C3's files: `game/battle-view.ts`, `game/battle-input.ts`, `game/scenes/BattleScene.ts`,
`game/ui/{BattleHud,BattleFx,BattleLayout,BattleMenuPanel,BattleMessageBox,Palette}.ts`,
`tests/unit/battle-view.test.ts`.

Per build-doc §16 G12, nothing here is stated in human engineering-hours.

## Deviations

| # | Spec ref | Deviation | Rationale |
|---|---|---|---|
| C3-D1 | build-doc §16 G11 | **`VIEW_TIMING` (game/battle-view.ts), the HP-band thresholds `HP_BAND_WARN` 0.5 / `HP_BAND_CRITICAL` 0.2 and `MONO_ADVANCE_RATIO` (game/ui/BattleHud.ts), every pixel offset in `game/ui/BattleLayout.ts`, and the WCAG sRGB luminance coefficients in `game/ui/Palette.ts` are NOT in `data/balance.json`.** | G11 governs constants the **sim** reads — anything a retune of balance is supposed to move. An animation duration in milliseconds, a colour-band threshold, a pixel offset and the W3C's published contrast formula are presentation: a balance retune must not be able to change how fast the bar drains, and re-pacing the battle must not be able to move a damage number — nor should either be able to change what "legible" means. Nothing in `core/` reads any of them, and `no_magic_numbers` (tests/gates/guardrails.test.ts) is scoped to `core/`, so this is an explicit narrowing of G11's letter rather than an unnoticed hole. Each is declared in one table with the reason written beside it. |
| C3-D2 | build-doc §9.7 / lane B | ~~The battle-sprite asset key is **assumed** to be `battle/<lineId>/<ageClass>/<front\|back>`.~~ **CORRECTED.** `battleSpriteKey` (game/ui/BattleHud.ts) now returns the manifest row's own asset id — `creature-battle/battle-<line>-<age>-<facing>`. | The original row was wrong in fact, not just in form: `tools/comfy/manifest.json` was already committed with 150 `creature-battle` rows at `assets/final/creature-battle/battle-cindril-j-front.png`, and `game/placeholder.ts::assetId` turns that into the texture key `creature-battle/battle-cindril-j-front`. The **measured intersection of C3's 162 keys with the manifest's 150 ids was ZERO**, so when the art landed every battle sprite would have gone on silently drawing a stand-in (`textureFor` falls back with no warning). The row also claimed the placeholder "names that exact manifest row"; it named a row that exists nowhere. The key is now derived by the manifest's own rule (`comfy-batch.ts::deriveRows`, `shortId = lineId.replace(/-line$/, '')`) and `tests/unit/battle-view.test.ts` asserts **set equality** against the committed rows in both directions, so either side moving turns it red. |
| C3-D3 | core/types.ts `actionRejected.reason` | **`illegalActionReason`'s strings are never drawn** — and, unlike the first two cuts, this is now true. The `rejected` step's `caption` is `""`; the diagnostic travels on `ViewStep.rejected.reason`, which no widget reads; `BattleScene.perform` records it into `lastRefusal()` instead of saying it; and `BattleMessageBox.say` no longer takes the `diagnostic` flag that MUTED a refusal rather than refusing it. | core/types.ts:425 says of that field: "it is a diagnostic, not player-facing copy (G7)". The first cut pushed it into the narration line from the MENU. The second cut removed it there and left it in the compiler — `caption: event.reason` — so the scene printed it anyway, `lastRefusal()` stayed empty, and the design was exactly inverted while the file's own header claimed it was implemented. Reproduced in the running game: committing a snare in a gym put `only a wild creature can be snared` on the narration line. Fixing it at the compiler (no caption to print) rather than at the scene (a guard someone can drop) is what makes the claim structural. **A player-facing refusal string would be content, and neither document provides one** — see the gap C3-G4 below. |
| C3-D4 | bible §11 items | **Bag / snare / bait rows are labelled by typesetting the id** (`itemLabel`, game/battle-view.ts): hyphens and underscores become spaces, each word is capitalised. | `data/` carries no item-name table — `balance.medicine` carries ids (`salve`, `tonic`), snare tiers come from `SNARE_TIERS`, and bait ids are bag keys. Typesetting an id coins no noun and adds no word, so G2 is untouched; `BattleMenuLabels.item` / `BattleViewNames.item` override it the day a name table exists. |
| C3-D5 | build-doc §7.4 renderer contract | **Every `ViewStep` carries `playerAt` / `enemyAt` / `lureActive`** — the display state of the fielded pair, and whether a Lure is up, at that point in the log. The scene paints from those, never from `BattleView.snapshot`. | `push(events, stateAfter)` advances the snapshot to the end of the whole reducer step before a single step is drawn, so any mid-playback read of it is a read of the future. Reproduced: a self-buff step painted the player at 0 HP two steps before the blow that emptied them was drawn. `lureActive` was added for the same reason when the enemy card grew its Lure chip (C3-D8). |
| C3-D6 | build-doc §7.4 / §10 | **The named test file executes `game/scenes/BattleScene.ts`** against a stub Phaser (`vi.mock("phaser")`), replaying whole recorded fixtures through the real scene. The stub now also records a `Text`'s CONSTRUCTOR style, not just `setColor`. | The first cut asserted the scene by reading its own source with regexes, on the stated grounds that it value-imports Phaser. Every one of the five MAJOR defects a later audit reproduced lived in that file and in `CombatantPanel`'s Phaser half — code no test executed. The style omission was the same shape of hole one level down: `CombatantPanel` sets every colour at construction and never calls `setColor`, so the hex it painted was invisible to the harness and the palette inversion could only be seen by opening a browser. The suite now reads the same property the audit read off the live page (`Text.style.color`) and measures contrast on it. The source scans are kept; they are no longer the only witness. |
| C3-D7 | build-doc §8.4 / gate B0 | **The role→swatch table in `game/ui/Palette.ts` was re-picked against the FROZEN palette, split so no role serves two surfaces, and is now bound by measured contrast.** New roles: `hpTrack`, `cursor`, `cursorInk`, `cursorInkMuted`, `cursorInkDim`, `textDisabled`. The battle screen is dark-plate / light-ink, matching every other scene. | Naming a swatch by id survives the B0 value swap; naming the RIGHT swatch does not. The table was chosen when `c01` was near-black and `c07` near-white; B0 made `c01` a mid grey and `c07` a dark taupe and **every ratio inverted**. Measured on the shipped file: a DISABLED menu row painted at 5.29 : 1 and a SELECTABLE one at 2.49 : 1 (the greyed rows were the bold ones), a card's own name sat at 2.49 : 1 under a "muted" readout at 3.81 : 1, and a half-health HP bar was 1.64 : 1 against its track. Two roles were doing contradictory jobs — `panelInner` was both the HP track (wants dark) and the cursor bar (wants light), `accent` was both the focused row's ink (read on near-white) and the crit/catch FX colour (read on near-black) — so no single value could be right. Tests now recompute every ratio from `data/palette.json`, including **through the real `menuPanelModel`**, which is the check the lane did not have: its green was evidence about the role table's shape, not about legibility. |
| C3-D8 | bible §3 Lure / build-doc §7.2 | **The enemy card carries a persistent Lure chip**, and the failed-snare caption says `not caught`. | `BattleState.lureActive` was tracked through the whole compiler and read by nothing: a Lure's entire on-screen life was a 260ms caption, in the mechanic that multiplies catch odds for the rest of the battle. The chip's LABEL is derived from content (the move whose effect is `{kind:"catchOdds"}`), so no move name is written in `game/` (§8.3 / G2); with no such move there is no chip rather than a coined word. Separately, `snareThrow`'s caption never consulted `event.caught`, so a failed throw and a successful one printed the same line — a miss read as a throw followed by silence. `not caught` negates core's own event name (`t:"caught"`) exactly as this file already negates `fleeAttempt`'s success ("could not escape"); no adjective and no judgement, so G7 is untouched. |
| C3-D9 | build-doc §7.2 bait / G3 | **`baitIdsIn` asks a POSITIVE question** (`isBaitTag`: is this id a species line id or one of core's `ROLES`?) instead of enumerating by exclusion, and a bait row's detail column shows core's own `BaitMatch` word for the fielded target. | Enumerating "every bag key that is not a snare tier and not a medicine" avoids a bait table (G3) by having a bait table's failure mode: every future bag item became a live, un-greyed bait row. Reproduced against the real reducer with one `relic-antler-shard` in the bag — offered `disabled:false, reason:null`, consumed on throw, and `snareThrown.chance` identical to the no-bait chance. `core/battle.ts` cannot catch it (`illegalActionReason` only asks whether the bag HOLDS the id; `performSnare` consumes whatever it is handed), and `core/types.ts` already declares `OwnedCreature.relicSlot`, so non-bait items are designed in. The positive test is build-doc §7.2's own definition of a bait tag, so it is still not a table. |
| C3-D10 | build-doc §7.4 renderer contract | **`ViewStep.hit.attackerUid` is an INFERENCE, and it is consumed when spent.** | It is the one thing the view needs that the log does not carry: `BattleEvent.damage` has no attacker, so it is read off the `moveUsed` immediately in front of it. That is exact for every event core can emit today (one `dealDamage` call site, reached only from `performMove`, right after its own `moveUsed`) but it was undeclared load-bearing coupling — a future damage with no preceding move (recoil, a reflected hit, an environmental tick) would have been credited to whoever last swung. Clearing the attribution after it is used makes the second such blow report `null`, which is the honest answer. Reported as C3-G7. |
| C3-D11 | build-doc §15 C3 seam | **`BattleSceneData.onFinished` is REQUIRED.** | This scene deliberately routes nowhere — it does not know whether the fight was launched over a paused overworld, from a menu or by the demo capture, and a `scene.start` guessed here would be C3 deciding C1's navigation. But "does not route" plus "optional callback" is a screen a caller can strand the player on: once the reducer reports an outcome nothing changes, `handleKey` returns early, and the scene never stops itself. Making the seam mandatory is the structural fix. `game/scenes/OverworldScene.ts` supplies it and does `scene.stop(battle)` + `scene.resume()`. |
| C3-D12 | — | **The narration line is re-purposed while the command menu is open** (`menuContextLine`, game/battle-input.ts). | `openMenu` never touched the message box, so the player chose their action under the previous turn's damage line, and once the snares pane closed **nothing on screen said which tier had been armed** — `armedTier` was private and no widget drew it, in the pane this lane's own header calls the largest lever there is on catch odds. The line is the armed tier plus the root menu's own word for the pane; every other pane clears it. (`BattleMessageBox.clear()` existed and had no caller.) |
| C3-D13 | — | **`BattleScene.performedCount()` is exposed**, and `lastRefusal()` never clears. | The suite counted performed steps by counting writes to the message label, on the grounds that `perform` says exactly one caption per step; that stopped being true when a step could decline to narrate and when the menu could write its own line. A miscounting cursor does not fail — it asserts against the wrong frame. `lastRefusal()` was likewise overwritten with `""` by the next menu render, so it read empty at exactly the moment something had been refused; it now only ever takes a non-empty reason. |

## Gaps in `core/` that C3 could not close (reported, not worked around)

| # | Where | What is missing | Consequence today |
|---|---|---|---|
| C3-G1 | `BattleEvent.levelUp` (core/types.ts:404) | The new **`maxHp` / `curHp`**. `core/battle.ts:944-945` raises both from `effectiveStats` — a rules function the view may not call. | The view re-reads `maxHp` off the `BattleState` the reducer returned (`BattleViewAbsolutes`), which is correct because nothing else changes `maxHp` inside one reducer step. **`curHp`'s matching rise is still not knowable at the moment of the level-up**: the card shows the pre-level `curHp` against the post-level `maxHp` for that one step and is corrected at the end-of-step resync. | C3-G2 | `BattleEvent.moveUsed` (core/types.ts:388) | The move's **target**. | `ViewStep.attack` has no `targetUid` at all. The first cut inferred "the other active battler", which is wrong for the five shipped self-targeting moves (harden / quicken / focus are `target:"self"`, regrow is a self-heal, burrow-roost a self-evade). A projectile or beam animation is not implementable until core logs the target. |
| C3-G3 | `BattleInput` (core/types.ts:319-328) and `BattleEvent.battleStart` (:386) | Any **trainer / gym-leader identity**. | A gym battle cannot be announced by the leader's name. It used to open "Gym battle: Nibbin" — the leader's first creature. It now opens "Gym battle" and stops, and `BattleViewNames.opponent` lets the caller supply the name. This lands on the never-cut gym demo beat, so it is the most visible of the three. |
| C3-G4 | build-doc / bible | Any **player-facing refusal copy**. | Per C3-D3 the diagnostic strings are not drawn and the `rejected` step's caption is empty, so a greyed row explains itself only by being grey. Writing a player-facing line here would be inventing content. |
| C3-G5 | `game/main.ts`, `game/scenes/OverworldScene.ts` (neither is lane C3's file) | ~~`BattleScene` is not registered in `SCENES`.~~ ~~**CLOSED** — lane C1 has since registered it.~~ **CLOSED FOR REAL.** | The previous "CLOSED" was false and was exactly the row a reader would rely on: registration is not routing. `BattleScene` was in `main.ts`'s `SCENES` list and **idle** — no `scene.start`/`scene.launch` for the key existed anywhere, and `OverworldScene`'s `onEncounter` hook, the seam that would have started it, was supplied by nobody, so walking Route 1 into an encounter printed a HUD toast and nothing else. Lane C2 has since closed it properly: `game/wild-battle.ts` builds the `BattleInput`/`BattleContext` and `OverworldScene.beginWildBattle` does `scene.launch(SCENE_KEYS.battle, data)` + `scene.pause()`, with `finishWildBattle` stopping the battle scene and resuming the overworld from `onFinished`. Verified in the current tree. |
| C3-G6 | shipped fixtures | Ten of the twenty-two `BattleEvent` kinds — `heal`, `statusApplied`, `statusTick`, `statusSkip`, `statusCleared`, `statChanged`, `itemUsed`, `levelUp`, `evaded`, `actionRejected` — are produced by **no** recorded fixture. | Those paths are covered by hand-built logs and by a synthetic one-of-each replay through the real scene, which is weaker than a recorded fight. This is not cosmetic: because no fixture contains an `actionRejected`, the caption scan over "every caption the fixtures produce" could never see the one path that piped an EXTERNAL string into the message box, and the C3-D3 defect survived two cuts behind that green. A fixture that heals, statuses, buffs, levels up **and refuses something** would make the whole compiler fixture-covered. |
| C3-G7 | `BattleEvent.damage` (core/types.ts) | The **attacker**. | `ViewStep.hit.attackerUid` is inferred from the preceding `moveUsed` (C3-D10). Exact today; one field on the event removes the inference entirely. |
| C3-G8 | `game/encounters.ts` (lane C2's file) / `tools/comfy/manifest.json` (lane B's) | Agreement on whether a **wild Ancient can be met below Elder**. | `core/lifecycle.ts:346` pins an owned Ancient to `"E"` and the manifest ships Ancients as one form (`artFormsOf` → `['E']`), so `battleSpriteKey` and the 150 committed rows agree exactly.
